hoobot · design review · revision 3

hoobot architecture

Architecture locked: B+ Revised Not started · no code changed 30 Sep 2026

hoocode is the engine and the server. hoobot is bots and surfaces.

  • hoocode gains hoocode app-server, a long-running server that speaks the Codex app-server protocol. It handles threads, approvals, profiles, safety rules and worker processes.
  • hoobot is one client process. It runs the Discord, Slack and GitHub adapters, routes messages to bots, links your accounts, and manages bot installs.
  • A bot is a hoocode profile plus hoobot routing.
  • The same safety rules apply to every client: hoobot, the Codex CLI, or a web UI. Policy lives in hoocode's core, so the terminal UI is covered too.

What decided it

With policy in hoocode's core and a stdio app-server, A′ and B differ in only where the daemon lives. You want hoocode's server usable without hoobot, and the terminal UI sharing threads with bots, so the daemon belongs in hoocode.

B+: the three changes

  1. R15: policy lives in hoocode's core, not the server. Grants, always-allow rules and the folder allowlist apply to the terminal UI, rpc, print and the app-server.

  2. R16: hoocode has four layers. Each can be tested on its own. The daemon only relays and supervises, because each worker is an L3 process.

  3. R17: hoobot sticks to the standard Codex protocol, plus an optional profile id. It is tested against the real codex app-server too.

Later (R18): the hoocode terminal UI becomes a daemon client, so it can open a bot's thread live.

L4  daemon      socket + WS · fan-out · approval routing · supervisor
L3  app-server  Codex protocol over stdio · one client
L2  policy core profiles · grants · always-allow · workspace allowlist
L1  engine      AgentSession, tools, sessions   (exists today)
  • Why separate worker processes: hoocode falls back to process.cwd() in about 14 places in core. Running several folders in one process would be risky.
  • Daemon crash: launchd restarts it and threads resume from JSONL. A running turn is lost and shows as interrupted.
  • If B is too heavy: fall back to A′ by moving L4 into hoobot. The Codex protocol is on both sides, so the move is cheap.

What this means

  • hoobot gets much smaller. It has no process pool, no policy engine and no session store.
  • hoocode gets much bigger. Most of the work moves to the hoocode repo.
  • One safety model. It's the same whether a turn comes from Discord, the Codex CLI or the web UI.
  • hoobot can't do anything until hoocode's server exists, which sets the build order.

Protocol and server

Revised 12-protocol.md · R1, R3, R9, R11

  1. hoocode app-server is a full server, modelled on codex app-server: a daemon with many threads and many clients. It sends events and approvals to every client on a thread, and the first answer wins.

  2. The Codex app-server protocol, as-is. Stock Codex clients are a real goal.

  3. Transports: stdio (tests, one client), a Unix socket with mode 0600, and a WebSocket on 127.0.0.1 with a token.

  4. Copy only the protocol from ../codex: its generated TS types and JSON schemas, pinned to a commit. Write the server in TypeScript. The Rust code is a reference. Codex is Apache-2.0, so keep its notice.

  5. Dialogs use item/tool/requestUserInput. Only the editor dialog needs a hoocode/* fallback.

  6. Any process running as your user is the owner. The socket's file permissions are the authentication.

  7. Extensions use hoocode/*, for profiles and policy. There are no hoobot/* methods.

Found in the Codex code

  • Fan-out is built in. thread_state.rs tracks which connections subscribe to each thread and sends requests to all of them.
  • Dialogs are covered. A question can have options, a free-text answer (isOther) and hidden input (isSecret).
  • Permission profiles already exist in Codex ([permissions.<id>] with extends). hoocode profiles should line up with them.

What a bot is

Revised 10-bot-model.md · T1, R5, R12

  1. A bot is a persona, not a connection.

  2. Adapters are shared plumbing. One adapter per surface account hosts many bots, routed by mention, channel or command.

  3. The persona is a hoocode profile: prompt, model, tools, folders and rules. Profiles are useful without hoobot.

  4. A bot = a hoocode profile + hoobot routing.

  5. A package has two sections. hoocode.profiles holds the persona and is read by hoocode, which asks you to grant tools. hoobot holds only surfaces and routing.

Discord adapter (1 token) ─┬─ @reviewer  → bot "reviewer" → profile "reviewer"
                           └─ @helper    → bot "helper"   → profile "helper"
Slack adapter   (1 token) ─── /hoo ask   → bot "helper"   → profile "helper"

Sessions, workspaces and processes

Revised 13-sessions-workspaces.md · T4, R6, R10

  1. Threads belong to hoocode's server. Start on Discord, then continue in the web UI or the Codex CLI.

  2. Each profile has a default folder, plus an allowlist of project folders. hoocode rejects any other path.

  3. The server is a thin supervisor with one worker per (profile, folder), each hosting many threads.

  4. Idle threads unload and resume from JSONL. A worker exits when it has no threads loaded.

  5. The link between surface threads and hoocode threads lives in hoobot. hoocode never learns about Discord.

hoobot's link store

// ~/.local/share/hoobot/links.json (or SQLite)
{
  "discord:1234567890":          { "threadId": "t1", "botId": "reviewer" },
  "slack:C01/1700000000.1234":   { "threadId": "t1", "botId": "reviewer" }
}

Two surface threads can point to the same hoocode thread. hoobot marks who spoke with a short label in the message, such as [discord: sachin].

Rules when several clients show one thread (hoocode enforces them)

  • One turn at a time. A message sent during a run becomes turn/steer.
  • Events go to every subscribed client. Discord shows a summary; the web UI shows everything.
  • Approvals go to every subscribed client. The first answer wins.
  • Session files are stored by hoocode, for example ~/.local/share/hoocode/sessions/<profile>/<thread>.jsonl.
Migration

The old discord-sessions/<id> folders are imported into hoocode as threads of the default profile. hoobot writes a discord:<id> link for each one.

Users, approvals and safety

Revised 14-users-safety.md · T5, R4, R11

  1. Single owner: you. hoobot links each surface account to you and ignores messages from unlinked IDs.

  2. Only you approve, from any client subscribed to the thread. hoocode routes the request.

  3. A package requests tools; you grant them when installing through hoocode. The worker gets only the granted tools.

  4. "Always allow" rules live in hoocode policy, per (profile, folder). They are never global.

  5. Server access: any process running as your user (socket mode 0600). WebSocket clients need a token.

  6. ChatGPT mobile relay: later, opt-in, off by default.

Five layers of protection

#LayerLives inStops
1Surface filterhoobotStrangers in a shared server
2Socket permissions, WS token + Origin checkhoocodeOther users, other websites
3Profile grants → worker tool listhoocodeA bot using tools it wasn't given
4Approval gate + always-allow ruleshoocodeUnapproved bash / edit / write
5Workspace allowlisthoocodeEscaping to other folders

Layers 2–5 protect every client, not just hoobot.

How an approval travels

  1. A worker asks hoocode's server to approve a tool call.
  2. The server checks the always-allow rules for this profile and folder. On a match, it approves.
  3. Otherwise it asks every subscribed client: hoobot shows Discord buttons, alongside the web UI, the Codex CLI and a menu-bar notification.
  4. The first answer wins: Accept, Accept for session or Decline.
  5. No answer in 10 minutes means Decline.

Policy record (hoocode side, sketch)

{
  "id": "reviewer",
  "requested": ["read", "bash", "edit"],
  "granted":   ["read", "bash"],
  "workspaces": ["~/github/hoobot", "~/github/other"],
  "alwaysAllow": {
    "~/github/hoobot": ["bash:git status", "bash:bun test"]
  }
}

Things to check

Needs your eye
hoocode gets big

The server, fan-out, supervisor, profiles and policy all land in hoocode. That is most of the project, and it's a larger change to hoocode than a new mode.

Keeping up with Codex

Codex changes its protocol often: the local clone was committed today. Pinning helps, but stock clients will expect newer methods over time.

Experimental API

item/tool/requestUserInput is marked experimental in Codex, so its shape may change.

Unix socket = owner

Any process running as your user can drive hoocode, including approving its own tool calls. That's fine on a single-user Mac, but it isn't a sandbox.

Shared folders

Two profiles in the same folder means two workers editing the same files. It's allowed, but the UI should warn.

Not verified

I read the Codex README, the schemas and thread_state.rs, not the full server. The mapping table is a plan, not tested.
